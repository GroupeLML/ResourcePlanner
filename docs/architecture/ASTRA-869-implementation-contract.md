# ASTRA-869 implementation contract — Phase 2A.1b.3a (Draft checkpoint)

Implementation of [ADR-039](ADR-039-mandatory-superintendent-cc-and-recipient-provenance-v5.md) and [ADR-017](ADR-017-erp-project-manager-and-rp-co-managers.md); this is not an ADR or amendment. The existing project_v2 envelope, v5 capability and P0–P4 algorithms are unchanged. Not operationally usable or deployable.

## Current-source identity and evidence

- ERP_EMPLOYEE is the exact canonical ERP EmployeID observed for a specific project principal. It is not constructed from names, email, legacy contact or arbitrary ERP-labelled BusinessContact. AUTHENTICATED_PRINCIPAL is the exact issuer/subject pair with an optional independently proven local AppUser association. These join the existing stable-link graph, including inactive/noneligible competing records. A contradictory component cannot establish cross-root equivalence.
- Person identity, role relationship, source-record address authority and observation scope are distinct. A direct candidate keeps its persisted root, raw address, activity and role. MessageRecipientInputs binds the role to the project; RP co-manager nomination is keyed by project and BusinessContact, separately from the ERP principal even when the identities are equivalent. Requesters use AppUser email, assigned employees use Resource email. The global superintendent population remains the canonical active/ERP-active Resource competency roster.
- RecipientAddressObservation validates the exact allowed source/record/scope combinations and derives single-mailbox resolution. Current Resource/Contact/User addresses and authenticated principal email have different source scopes. Raw-address contradictions for the same source record and scope fail closed. Generator evidence contains only issuer, subject, optional local association, display name and the authenticated email observation; no credential or token. The existing generator identity fingerprint algorithm is preserved.
- ERPManagerAuthority retains the canonical project principal, optional linked user with activity, resolved/absent/unresolved contact status and contact email, and separately proven unique Resource fallback with both activity flags. Usable contact wins; only missing contact address/absent or unresolved contact permits proven fallback. Nonblank invalid/ambiguous/injected contact address does not fall back. Inactive resolved manager user or contact blocks the manager; inactive fallback Resource alone does not block delivery but cannot be a mandatory eligible superintendent. No AppUser-email substitution. Direct resolved contact authority is not discarded merely because a cross-root link is ambiguous; unproven fallback is rejected.
- The existing identity-first then normalized-address composition primitive is reused; To precedes CC, with manager then co-manager then requester precedence. Inputs preserve every role and raw observation including suppressed/invalid address sources. Valid transport contributions retain canonical roots; mandatory missing address is fulfilled only through proven identity delivery, not names/address coincidence. Generator is optional and typed; a proven To suppresses its separate CC address but retains its contribution.
- Canonical serialization records explicit observations, role evidence, generator identity fingerprint and recomputed envelope/provenance. Strict readers reject unknown/missing keys and contradictory derived claims. These provisional undeployed v5 shapes are intentionally changed; no persisted-data rewrite or migration is authorized.

## Intermediate compatibility and remaining work

The inactive Phase 2A capture remains contact-rooted for managers; it is explicitly marked provisional in role evidence and does not claim independent ERP authority. Its generator/ERP-only rejection paths remain. Neither this compatibility path nor typed domain constructors prove actual persisted-source capture. Phase 2A.2 must source the typed authorities from canonical server data and prove identity closure, exact namespace, role nomination, eligibility and coherent bounded reads; no client-supplied authority is permitted.

## Phase 2A.1b.1 — current-state fingerprint checkpoint

- P5 now hashes the complete current P4 business semantics plus current population, current stable-link evidence, all current project source inputs and their generator-independent resolution. Current project role and manager validation use the same current-only index. The optional authenticated generator and its original identity fingerprint are excluded from this authority.
- Generator-only identity closure is an explicitly separate immutable evidence field. The composition graph may add an authenticated principal linked to a current user or a disjoint generator-only stable-link component. Any added persisted fact connected to a current component (including an ambiguous component) contradicts the required complete current closure and fails closed; unrelated, duplicate or unlinked extension evidence is rejected. Actual persisted-source capture must prove both closures separately in Phase 2A.2.
- Provisional per-project recipient results are separately recomputed with the generator and its composition-only evidence. Their canonical digest covers the current source context, generator identity and option, extension and derived envelope/provenance. The strict reader verifies both current resolution and provisional composition claims and the digest. The digest is not a reviewed message/content fingerprint and does not establish actual generated-message coverage or independently persisted prepared-content integrity.
- The current project source coverage remains complete even when later delta selection produces no message. Existing provisional per-project results are not actual generated-message evidence; no removed-project observation or composition is implemented in this partial checkpoint. Phase 2A.1b.2 implements the separate inactive message-context representation described below. Phase 2A.1b.3a implements actual included-message recipient composition; Phase 2A.1b.3b must implement final composition/envelope and reviewed-content fingerprints. Operational composition and lifecycle integration remain later.
- Current-state P5 and provisional v5 serialized shapes intentionally change for this inactive, undeployed capability. Earlier provisional shapes without the explicit separated fields fail closed; no persisted artifacts are converted. P0–P4 shapes and fingerprint algorithms, baseline selector, both generation guards, and live v4 behavior remain unchanged.

## Phase 2A.1b.2 — inactive historical message context

- `communication_message_context.py` defines separate immutable domain evidence over independently supplied current v5 and communicated baseline snapshots. Full mode derives eligible message keys from all current projects; delta mode calls the existing `compare_project_communication_projections` without another selection algorithm. The canonical key is `project:<project_id>`. Each eligible context retains its mode, change kind, applicable historical before and current after sources, and an explicit whole-message included flag. Exclusion keys must be unique, canonical and within eligible coverage. No current project or Shift is synthesized for a removal. No-message and all-excluded evidence is not prepared-batch approval.
- A delta reference contains the trusted communicated row ID, week boundaries, model/status and existing snapshot fingerprint; the independently supplied immutable baseline must match its reference. The reader compares all claimed references, sources and coverage against reconstructed facts, including a changed batch ID with identical snapshot fingerprint. Full mode has no applicable delta reference. This is not another baseline store or proof of selecting the latest database row. The existing selector remains unchanged; later operational integration must obtain the row ID from that same authoritative selection and revalidate the applicable reference.
- Each project source retains snapshot presentation participants with role, recorded contact/user/Resource IDs, activity, captured address and explicit CURRENT/HISTORICAL origin; a historical source retains the originating reference. P0–P4 observations with no recorded identity remain unknown; a recorded contact/user root is not proof of an ERP principal or historical alias. A recorded assigned Resource ID is direct identity evidence. For v5 the source also retains the original typed project inputs, raw observations and relationship evidence, and selected candidate/root resolved solely with that snapshot's generator-independent index. For a historical v5 source, the nested original capture scope describes the then-current source; the enclosing source and typed observation explicitly mark its historical origin. No historical identities or aliases are enriched from current tables, names or addresses. Repeated contradictory scoped participant facts fail closed.
- `supports_mandatory_resource` only indicates valid address evidence for a proven direct or frozen canonical Resource identity; it cannot establish fulfillment of an actual envelope. Unknown or legacy contact/user-only historical evidence cannot discharge a mandatory Resource blocker, even when the current graph links that contact/user or names/addresses coincide. Distinct before and after addresses remain separate. Final selection, deduplication and mandatory fulfillment for included messages are Phase 2A.1b.3/operational integration obligations.
- Current policy and original requested generator are obtained only from the independently supplied current snapshot's recipient policy context, including its existing provisional composition digest. Historical global rosters and generator options are never unioned or copied into current policy. The before/after observations carry project roles only. Existing P5 and snapshot JSON remain unchanged and do not incorporate this separate message-context object or selection.
- Canonical JSON serialization and strict deserialization rederive all fields from independent current/baseline evidence, validate exclusions, reject unexpected/missing/contradictory claims and duplicate JSON keys. This validates represented source/coverage facts, not the integrity of a coordinated change to otherwise legitimate inclusion selections; final actual composition/envelope/reviewed-content fingerprints and operational prepared-artifact authority remain Phase 2A.1b.3 and later. No operational persistence or generation call has been introduced.

## Phase 2A.1b.3a — inactive actual-message recipient composition

- `communication_actual_message_recipients.py` derives immutable actual recipients only from independently validated MessageContextEvidence.included_messages. Eligible keys remain separately represented; excluded projects, unchanged deltas, and empty outcomes do not generate envelopes. No approved/prepared claim, draft, operational persistence or external delivery. The authoritative construction/reading boundary is ActualMessageComposition, not independently instantiated subordinate data classes.
- Scoped observations retain the original source position and identity, origin-local canonical identity, role/channel, captured raw address and source, activity and resolution. Typed evidence is retained in the independently validated context. Historic P0–P4 addresses are explicitly HISTORICAL_CAPTURED_ADDRESS, not a fabricated raw Resource/Contact/ERP authority; absent identity stays unknown. A typed manager with no local participant IDs still uses its typed ERP authority. Unresolved untyped presentation rows cannot select an address.
- Preserve ADR-037 ordering: all applicable current To precede historical To; manager, co-manager and requester ordering within each project remains the accepted source order. Old-only assigned employees remain eligible; a same-ID assignment's current contact supersedes the historical contact, including missing/inactive current values. Superseded observations remain inspectable and may contribute provenance but cannot select delivery. Assigned CC order is deterministic, followed by the original current generator and then current mandatory roster.
- Identity selection uses independently resolved canonical roots. No cross-time union of identity graphs. A historical observation that has only its recorded root can contribute to an already selected current observation of that identical recorded root, without changing its historical canonical claim or transferring the current alias into history. Different independently established canonical roots are not joined through a common raw root. Unknown observations have separate keys. Transport-address deduplication is a second stage with casefold normalization and To precedence; each merged identity retains its own selected observation and contributing indices. A shared address is not identity proof.
- Mandatory population comes exclusively from current policy and uses the frozen v1 mailbox resolver, captured population resolution and MandatoryResolution diagnostics. Existing delivery is fulfilled only by a valid independently selected identity group for the exact Resource key that survives into the actual envelope; valid distinct identities sharing one address retain separate selected proof. Neither a superseded assignment, invalid current observation, unknown historical identity nor historical contact/user-only evidence can discharge a blocker through shared address or today's graph. Missing/inactive/invalid existing To diagnostics are blocking; assigned CC diagnostics remain warnings. Binding failure and employee-specific blockers remain explicit. Current generator uses the accepted current composition index; old roster/generator are excluded.
- Canonical scoped-v1 JSON includes independent message context, eligible/included keys, all derived actual recipient observations, identity selections, envelope, mandatory proof and diagnostics. Strict reader rederives the entire representation and rejects missing, duplicate, forged or contradictory claims, including incorrect selection indices or false fulfillment. No final content/envelope fingerprint, reviewed content or prepared-artifact validation is implemented here; a coordinated replacement of the trusted input context itself is outside this structural check. Existing P0–P5 serializers/fingerprints, provisional composition v1, live v4 and both v5 guards remain unchanged.

Phase 2A.2 and later phases must prove real persisted manager matrix and generator source capture, current-state vs composition lifecycle, latest COMMUNICATED same-week baseline, removed-project messages, approval/delivery operator independence, frozen reviewed envelopes, retry/idempotency, employee correction/regeneration, and legacy cutover. Real SQL Server multi-session coherence, collation, identity, bounded queries and JSON persistence evidence remain mandatory. A shared Session alone is not proof of a coherent transaction-wide read. Both operational v5 rejection guards remain; live scheduling generation remains v4. No migration, external delivery, startup or configuration changes.
